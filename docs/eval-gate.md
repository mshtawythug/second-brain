### Eval gate (CI)
The eval-marker harness (`tests/test_eval_harness_live.py`) is **excluded from the default pytest invocation** (`pyproject.toml` → `addopts = "... -m 'not eval'"`). Rationale: it requires a live Postgres + Ollama and would slow every local `pytest` run. (It no longer carries per-query threshold assertions — see "What CI actually enforces" below.)

**What CI actually enforces — read this before assuming the gate gates.** `.github/workflows/eval.yml` runs **harness health only**. The retrieval-quality regression gate is a **LOCAL pre-merge check**, keyed to one machine's document set, and on a GitHub-hosted runner it is structurally unable to run. That is a property of the gate, not a missing chore: scoring retrieval needs four things a hosted runner does not supply — (1) `tests/eval/golden_corpus.yaml`, which is gitignored by design, and whose absence makes `brain eval` exit `1` in `load_corpus` before it opens a DB connection; (2) an initialised schema, since the job never runs `brain init`; (3) populated documents whose UUIDs match the baseline's, which a fresh ingest would not produce; (4) a reachable embedder, and there is no Ollama on a hosted runner. Committing `ci.json` does not change any of the four. The gate step therefore requires **both** `ci.json` and `golden_corpus.yaml`, so it self-arms only on a machine that can genuinely run it.

**The only configuration that would gate real retrieval quality is a self-hosted runner attached to a live brain** — not currently set up, and probably not worth it for a personal project; recorded here so the question stops being re-asked.

`.github/workflows/eval.yml` runs on every PR, every push to `main`/`master`, and manual `workflow_dispatch`:

1. Brings up the pinned Apache AGE test instance pull-first: `docker compose -f docker-compose.age-test.yml pull --quiet || true`, then `up -d` with no `--build`, which compiles AGE from the compose `build:` stanza only when the pull missed (the same idiom as `ci.yml`, locked by `tests/test_age_image_pull_first_contract.py`) (PostgreSQL 16 + pgvector 0.8.6 + AGE, port **5434**, db `second_brain_test` — the same instance the local test suite uses). A GitHub Actions `services:` block can't `build:` an image inline, so compose is used instead of a service container; one eval-marked test reaches the AGE-backed graph layer.
2. Installs the package with `pip install -e ".[dev]"` and waits for `pg_isready` on port 5434.
3. Runs `pytest -m eval --no-cov -v`. The eval-marked tests SKIP cleanly without a live corpus + Ollama, so in CI this is import/collection regression coverage — it turns red only when the harness itself breaks.
4. Conditionally runs `brain eval --baseline ci --diff --fail-below`, but only when **both** `tests/eval/baselines/ci.json` and `tests/eval/golden_corpus.yaml` exist. On a hosted runner the corpus is always absent, so this is always the skip branch. Locked by `tests/test_eval_workflow_contract.py`.
5. Tears down the AGE instance with `docker compose -f docker-compose.age-test.yml down -v` (always, even on failure).

**Decision recorded (Wave A.1, corrected 2026-09-02):** the eval marker stays OFF in the default `pytest` invocation. The original wording said "Gate lives in CI only" — that was wrong in a way that cost real time, because it implied the gate was one recorded baseline away from working. Retrieval-quality gating lives **locally**; CI covers harness health.

**Decision recorded (2026-10-12):** the hermetic-gate options (FTS-only synthetic corpus, deterministic fake embedder, self-hosted runner; see `docs/handoff/2026-09-29-eval-baseline-and-pr-merges-handoff.md` §3.3) were considered, and the user chose to leave the retrieval-quality gate local — there will be no hermetic CI gate.

#### The committed `ci.json` baseline — three things that will bite you

1. **It is keyed to one machine's brain.** The baseline stores the document UUIDs it ranked. On any other machine — or after a destructive re-ingest here — nothing resolves, every metric scores `0.0`, and `--fail-below` exits `3` reporting a catastrophic regression that is really just a different corpus. **A spurious exit 3 almost always means the corpus moved, not that search got worse.** Check `brain status` document counts before believing the numbers. A document set that has only *grown* still moves rows, because new documents compete against judgments that never saw them: the 2026-10-13 re-record was this case, not recency drift alone. +608 docs (Krisp 2026-10-05, Confluence import 2026-10-08) moved 12 non-recency rows, and means fell 0.4834/0.5835/0.7267 → 0.2589/0.3697/0.5852 (nDCG@5/MRR/Recall@20). The golden judgments predated ~30% of the document set, so absolute scores understated quality until `golden_corpus.yaml` was re-judged. The two `recency` rows were re-judged on 2026-10-21 (item 2) and the other 29 on 2026-10-22, against 2,068 documents: 15 rows gained judgments (+67, 38 of them in row 15, now 53 judged), 14 are unchanged, none was removed. A Krisp ingest ran during the work (2,029 → 2,068); its new transcripts were judged too. `ci.json` was re-recorded after the count stopped moving, and the means went 0.3253/0.4310/0.7581 → 0.3191/0.4645/0.7176 (nDCG@5/MRR/Recall@20). Recall@20 falls because the larger judged sets include documents that rank below 20. That is the judgments catching up with the document set, not a regression. Method and counts: README (1), "Re-judged 2026-10-22", and `docs/plans/2026-10-22-golden-corpus-rejudge.md`.
2. **Two `recency` queries were clock-dependent until 2026-10-15, when they were pinned to absolute dates (see the end of this item).** They filtered on `documents.ingested_at` via `since_days: 40`, so the matched set is stable only while `today − 40d` stays inside one gap in this brain's ingest history. Re-recorded **2026-10-13** inside a 21-day gap (2026-08-31 → 2026-09-21), so its *trailing* edge holds for roughly **2026-10-10 → 2026-10-31** (re-recorded again the same day for the vector-leg ranking change, same window). Re-recorded **2026-10-14** because the document set moved (7 vault notes synced: 6 daily briefs + `index.md`); only the daily-brief query changed, and the means went 0.2779/0.3826/0.7112 → 0.2724/0.3826/0.7089. **The gap only protects the trailing edge.** The *leading* edge moves whenever a document is ingested, and that query's top 20 on 2026-10-14 and all of its judged documents (28 then; 27 since the 2026-10-21 re-judge) are daily briefs, so every daily brief the vault watcher syncs was an unjudged competitor: in the `since_days` era (until 2026-10-15) that one query (and so the mean) drifted on most days a brief landed, an exit 3 with every non-recency row unchanged, and that was known drift, not a regression; outside the window, or after new briefs, the baseline needed re-recording. **None of that applies to the pinned queries** (below): an exit 3 where only a recency row moved is no longer automatically the known drift — investigate it (README (2)). For a query still on `since_days`, the window is a property of the corpus — re-derive it with the SQL in `tests/eval/baselines/README.md` before re-recording. The first recording (2026-09-02) drifted on 2026-09-20 exactly as predicted: one query, every other row unchanged. **Fixed 2026-10-15, and applied the same day.** A golden-corpus entry can now pin `after:`/`before:` (`YYYY-MM-DD`; `hybrid_search`'s own bounds on `coalesce(sent_at, ingested_at)`, inclusive/exclusive at UTC midnight) in place of `since_days`. A closed range whose `before` is already past when the baseline is recorded (`before` ≤ that day's UTC date, `after` = `before` − 40) drifts on neither edge. Given that no candidate is dated after `now`, which a past `before` guarantees, the recency boost keeps the ranked order clock-invariant. A `before` of tomorrow reopens the leading edge until UTC midnight. `load_corpus` refuses `after` without `before`, `after >= before`, and either one mixed with `since_days`. A positive-int `since_days` still loads and still drifts; `true`, `40.7` and `'40'` (once coerced to 1, 40 and 40) and `0` and negatives (once passed through as no window and a future-starting window) are now refused, so a corpus carrying one exits `1`. **Applied 2026-10-15:** both entries in the local, gitignored `golden_corpus.yaml` were converted to `after: 2026-09-05` / `before: 2026-10-15` in place of `since_days: 40`, and `ci.json` was re-recorded (trigger: an edit to `golden_corpus.yaml`). The means were unchanged at 0.2724/0.3826/0.7089. Only one row's top 20 moved: four Krisp meetings ingested 2026-10-05 but sent in July/August fell out under the new filter column. That row still scored 0.0, because none of its judged documents was in range. The judged documents outside the range were 18 of 28 for the daily-brief query and 5 of 5 for the other. They could never be retrieved, so they capped both rows. The `since_days` window already excluded the same set, so this was a re-judging task, not a regression. **Re-judged 2026-10-21** (trigger: an edit to `golden_corpus.yaml`). The daily-brief query keeps its range and now judges the 27 briefs dated inside it. The planning query had no on-topic document in its range, so it was re-pinned to `after: 2026-07-24` / `before: 2026-09-02` rather than re-judged. Those are the dates of the first recording's window, not its document set: 137 of the 162 documents now in that range (measured 2026-10-21) were ingested after that recording and are dated back by `sent_at`. The 2026-10-21 re-pool of the range is what confirms the five judgments. Both are now fully in range (27 of 27, 5 of 5), no other row moved, and the means went 0.2724/0.3826/0.7089 → 0.3253/0.4310/0.7581. Detail in README (2), "Re-judged 2026-10-21". A pinned row still moves when the document set changes inside its range (trigger: an ingest), and rarely from an ingest outside it, through the approximate vector leg (README (2)). How to choose the dates, plus a check that the judged documents fall inside the range: README (2). Design: `docs/specs/2026-10-15-eval-recency-determinism-design.md`.
3. **A config change is indistinguishable from a quality regression in the exit code.** Changing the embedder, `recency_halflife_days`, `vector_sim_floor`, or `snippet_context_tokens` moves every metric. `--fail-below` still exits `3`; the *message* now names the changed keys (see below), but the exit code alone cannot tell you which happened.

**Who re-records it, and when.** Whoever makes the change that invalidates it, in the same PR — the same rule as any other committed fixture. Re-record after: any ingest or deletion that changes the document set, a re-embed or embedder swap, a change to any key in `config_signature`, a change to the ranking code (SQL or fusion), an edit to `golden_corpus.yaml`, or drift past the recency window above (queries still on `since_days` only; a pinned `after`/`before` query does not drift).

**Updating a committed baseline:**
1. Locally with a populated brain + Ollama: `brain eval --record-baseline ci`. It refuses (exit `1`, nothing written) if any query's embed call failed *transiently* (a timeout, a dropped connection, HTTP 408/429/5xx — on any backend); free the embedder and retry. A *permanent* embed failure (model not pulled, bad API key) aborts the run with exit `1` before any report: fix the configuration, a retry will not help.
2. Inspect the diff: `git diff tests/eval/baselines/ci.json`
3. Commit the new baseline JSON alongside the change that justifies the new numbers, and say in the commit message *which* of the triggers above applied.

The `--fail-below` flag exits with code `3` (distinct from `1` = generic error and `2` = Typer BadParameter) when any mean metric — nDCG@5, MRR, or Recall@20 — regresses by more than `1e-4` (one unit at the baseline's 4-decimal serialization precision). Uniform threshold across all three metrics — no per-metric overrides (kept simple; the one downstream consumer is the CI workflow). `--fail-below` requires `--diff`; passing it alone exits `2` (Typer BadParameter). A **degraded** run, meaning one or more queries whose embed call failed *transiently* on any backend (an `EmbedError` with `transient=True`: a timeout, a dropped connection, HTTP 408/429/5xx) and scored `0.0` without being measured, is never recorded or judged: `--record-baseline` exits `1` without writing, and `--fail-below` exits `1` when a query the baseline also has is degraded (`degraded_queries`, which `--diff` leaves out of the deltas). A degraded query that is new since the baseline is outside the comparison and does not block the gate. Plain runs and plain `--diff` still exit `0`, and every run with a degraded query warns on stderr with the count. A *permanent* embed failure (model not pulled, bad API key, `OllamaEmbedContextOverflow`) is not a degraded row: the run stops with exit `1` before any report. See `tests/eval/baselines/README.md`.

`tests/eval/baselines/.gitignore` ignores `*.json` by default; explicitly-named committed baselines (currently `ci.json`) are allowlisted with `!ci.json`. Add new committed baselines the same way — do not blanket-allow.
