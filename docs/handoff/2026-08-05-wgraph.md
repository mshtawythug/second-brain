# Handoff — wgraph → w2b, 2026-08-05

## `brain_search` is the only MCP handler that writes without `autocommit`

**Priority: low. Production is not affected.** This is a consistency + latent-risk
fix, not an outage. Please don't let it jump the F6 queue.

### What

`src/brain/mcp_server.py:428` opens `with _mcp_conn(state) as conn:` for the
`brain_search` tool and never sets `conn.autocommit = True`. It then calls
`record_search_query(conn, ...)` at line 502.

An AST audit of all 29 `with _mcp_conn(...)` blocks in the file:

| block | writes | sets `autocommit` |
|---|---|---|
| line 428 `brain_search` | yes (telemetry) | **no** |
| line 881 | yes | yes |
| line 1086 | yes | yes |

`brain_search` is the lone exception.

### Why it matters

`brain.db.connect` is a `@contextmanager` whose exit path calls `conn.close()`
and nothing else — there is no `commit()`. psycopg rolls back on close, so an
uncommitted write through it is discarded. Measured directly, not inferred:

```
with connect(URL) as conn:                 -> rows surviving: 0
with connect(URL) as conn:                 -> rows surviving: 1
    conn.autocommit = True
```

`_mcp_conn` yields the persistent `autocommit=True` connection when
`state.db_conn` is set, and falls back to `connect()` when it isn't.

- **Production: unaffected.** `main()` always supplies a `PersistentConnection`,
  so the row lands today.
- **Tests: affected.** 22 of the 24 MCP test modules build `_State` without
  `db_conn`, so every `brain_search` telemetry write is silently discarded
  there. Confirmed by running the real handler on the fallback state:
  `MUTATION fallback rows=0`.

The sharper argument is that it already violates a documented precondition.
`brain.gaps.record_search_query`'s own docstring:

> *"A single parameterized INSERT. **Callers run with `autocommit=True`** so this
> is one round-trip; logging must never slow or break the search response."*

`brain_search` is a caller that does not. And because `record_search_query` is
best-effort by design — it swallows `OperationalError`, `UndefinedTable`, and
`UndefinedColumn` — nothing ever complains. Two silencers stacked: the writer
swallows failure, and the connection discards the write. That combination is how
a feature dies without a single red test.

### Proposed patch — one line

Insert as the **first statement** inside the `with` block, before any query
(psycopg raises if autocommit is set with a transaction already open):

```diff
--- a/src/brain/mcp_server.py
+++ b/src/brain/mcp_server.py
@@
     try:
         with _mcp_conn(state) as conn:
+            # record_search_query documents `autocommit=True` as a caller
+            # precondition, and brain.db.connect() closes WITHOUT committing —
+            # so on the non-persistent fallback path the telemetry INSERT is
+            # silently discarded. Matches every other writing _mcp_conn block.
+            conn.autocommit = True
             person_match = None
             if person is not None:
```

Safe on both paths: the persistent connection is already `autocommit=True`
(assigning the same value with no open transaction is a no-op), and the fallback
connection has no transaction open at that point — `connect_raw` issues its
`pg_type` probe and then `conn.rollback()`s before returning.

Reads are unaffected: `hybrid_search` only SELECTs, and `record_search_query`
already wraps its INSERT in `conn.transaction()`, which under autocommit begins
and commits a real transaction rather than taking a savepoint.

### Tests already in place (mine, no source changes)

`tests/test_mcp_telemetry_durability.py` — 5 passed:

- `test_mcp_search_telemetry_row_lands` — asserts the row is readable **from a
  separate connection**, the only evidence distinguishing a landed write from a
  discarded one.
- `test_reading_back_on_the_writing_connection_would_not_prove_landing` — pins
  that the read really is on a distinct connection, so the assertion above can't
  decay into reading its own uncommitted row.
- `test_no_new_mcp_handler_writes_without_autocommit` — AST guard. Deliberately
  a **subset** assertion keyed on `KNOWN_NON_AUTOCOMMIT_WRITE_BLOCKS`, so
  **applying the patch above keeps it green** rather than flipping it red. A new
  offender turns it red.
- `test_connect_context_manager_does_not_commit` — pins the root cause so the
  rationale is executable rather than folklore. Note this one asserts `connect()`
  does **not** commit; several callers rely on that, so it is documentation of a
  deliberate design, not a bug report.

Nothing in `src/` was touched by me. Over to you.

## Why three should stay unwired

**`cli_docs.py:205` and `ui/notes_service.py:386`** pass `new_draft=` and nothing
else. There is no content argument, so a guard has nothing to scan. Wiring them
would be pure ceremony — it would read as coverage while protecting nothing,
which is worse than leaving them visibly unwired.

**`demo/__init__.py:192`** ingests `brain/demo/corpus/manifest.json` — 22
synthetic documents shipped inside the package. No user content can reach it.
Scanning our own constants on every `brain demo` costs startup time, and a false
positive (these regexes do fire on legitimate prose) would break the
zero-friction onboarding path the command exists to be.

That reasoning depends on the shipped corpus actually being clean, which is an
assumption about an editable data file. So instead of wiring a guard that can
only scan constants, I asserted the property the decision rests on:
`tests/test_demo_corpus_secret_free.py` — **23 passed** — runs the real
`scan_secrets` over every packaged record. If someone adds a secret to the
manifest, that test fails and the decision gets revisited deliberately rather
than silently becoming wrong.

## Caveat on `vault/sync.py:797` — do not wire this one blind

`SecretGuardError` is caught **nowhere** in `vault/sync.py` or
`vault/watcher.py` (grep: zero hits). Under `BRAIN_SECRET_GUARD=reject` a single
offending file would therefore abort the whole sync — and, since the same path
runs under `brain vault sync --watch`, could take the watcher daemon down. The
guard's own docstring already names this failure mode as the reason `warn` is
the default:

> *"silently mutating (`redact`) or aborting a 900-file walk (`reject`) are both
> worse failures than a loud message."*

`redact` has a second problem here specific to vault tier: it would store a
redacted body while leaving the user's own file untouched, so the vault file and
the DB row would silently diverge — and vault-tier notes treat the file as
authoritative.

**Recommendation:** wire it, but catch `SecretGuardError` per file inside the
walk and report it as a skipped-file diagnostic in `SyncReport`, the same way
other per-file failures are handled. Wiring without that turns one bad file into
a dead daemon. Owner: w3.

## Routing

  confirming the decision) → **w2b**
- `cli.py:5437`, `cli.py:5658` → **coordinator**

# Task #14 — FTS double-stemming: two more sites need the same one-line fix

`_build_tsquery` returns **lexemes** (`plainto_tsquery(…)::text`). Any consumer
that binds them as `to_tsquery('english', %s)` stems them a *second* time and the
result stops matching the stored `tsv`. Fixed in the modules released to me;
two remain, owned by others.

## Measured on the live corpus (1376 docs, read-only)

```
lexeme:      'provis'          -- plainto_tsquery('provisioning')
restemmed:   'provi'           -- to_tsquery('english', 'provis')   <-- the bug
stored tsv:  'provis':1
match now:   false
match fixed: true
```

End-to-end on the real corpus, `provisioning`:

```
BEFORE (to_tsquery re-parse) chunks matched:   1     -- noise: something stems to 'provi'
AFTER  (::tsquery cast)      chunks matched: 267
```

**Three distinct failure classes**, not one:

1. **re-stemming** — `provis`→`provi`. 3.2% of the 2000 most-frequent corpus
   lexemes, including `databas`, `respons`, `decis`, `convers`, `releas`,
   `enterpris` — ordinary query vocabulary.
2. **re-parsing of hyphenated compounds** — the stored single lexeme
   `interview-prep` came back as the phrase
   `'interview-prep' <-> 'interview' <-> 'prep'`, which cannot match it. Also
   `competitive-strate` (3414 docs), `job-rel`, `multi-ten`, `end-to-end`,
   `follow-up`.
3. **stop-word annihilation** — `own` (400 docs) re-parsed to the **empty**
   tsquery, silently deleting the term.

Because `plainto_tsquery` AND-s terms, **one** affected word zeroed the entire
FTS leg. Under `BRAIN_EMBEDDER=none` that returned nothing at all.

Note quoting is **not** a workaround — `to_tsquery('english', '''provis''')`
still yields `'provi'`. Only the `::tsquery` cast preserves lexemes.

## Fixed (mine)

- `src/brain/search.py` — `ts_rank(c.tsv, %s::tsquery)` / `c.tsv @@ %s::tsquery`
- `src/brain/graph_rag/_retrieval_common.py`
- `src/brain/graph_rag/global_.py`

## Still to fix

### 1. `src/brain/facets.py:47` and `:92` — owner w3

```diff
-    WHERE c.tsv @@ to_tsquery('english', %s){fts_filter}
+    WHERE c.tsv @@ %s::tsquery{fts_filter}
```

Its own docstring already documents that `tsquery` comes from
`brain.search.build_tsquery`, so the input contract is not in doubt. **This one
matters for correctness of the numbers, not just recall:** facet counts are
computed from the same tsquery as the ranked rows, so while facets double-stem
and search does not, the counts describe a *different match set* than the
results shown — precisely the divergence the `build_tsquery` docstring says the
shared helper exists to prevent.

### 2. `src/brain/wiki/build_related.py` — owner unclear (wiki/)

`_to_tsquery_text` (line ~663) re-feeds `ts_stat`-derived lexemes through
`to_tsquery`. Its docstring states the intent plainly:

> *"`ts_stat` returns already-stemmed lexemes … We re-feed them through
> `to_tsquery` so the result is always a well-formed tsquery fragment."*

Well-formed, but re-stemmed. **This is the worst-affected site: 14093/86463
(16.3%) of `ts_stat` lexemes are stem-unstable** — a higher rate than search,
because `ts_stat` samples the whole vocabulary rather than the frequent head. So
roughly one in six "related documents" signals is silently dropped.

The fix is not simply swapping the cast, because the function's stated job is
*validation* (returning `""` for unsafe input) as well as construction. Suggested
shape: keep the `re.fullmatch` guard, then validate by casting rather than
re-parsing:

```python
row = conn.execute("SELECT (%s::tsquery)::text", (lexeme,)).fetchone()
```

That still rejects malformed input (the cast raises, catch it) without stemming
a second time. Worth a quick check of `build_related`'s output before/after — it
should get strictly more related-doc signal.
