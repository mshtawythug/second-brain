### Two design decisions that differ from the section text

**(a) `is_hosted_embedder` is duck-typed, not `isinstance(embedder, VoyageEmbedder)`.**
The plan specifies the `isinstance` form *and* requires a test double that
`is_hosted_embedder` recognizes without monkeypatching `VoyageEmbedder`. Those are
mutually exclusive — constructing a real `VoyageEmbedder` needs an API key and a live
client. Resolved by a class flag `hosted_egress: bool = True`, read via
`getattr(embedder, "hosted_egress", False)`, mirroring the established
`NullEmbedder.produces_embeddings` precedent. Open/Closed is preserved: a new hosted
backend declares the flag, and
`tests/test_sensitivity_egress.py::test_voyage_is_the_only_hosted_production_backend`
asserts each production backend's status explicitly so one cannot be added silently.

**(b) The re-ingest path ESCALATES ONLY — it never downgrades.** Not in the spec;
added because omitting it is a silent security hole. `sensitivity` defaults to
`normal`, so at `_update_doc_in_place` an incoming `normal` is ambiguous: it means
either "user asked for normal" or — far more often — "no flag was passed". Treating it
as authoritative the way `draft` legitimately is would mean **every** re-ingest
(a repeated `brain ingest`, any `brain vault sync --watch` pass) resets the column, and
the next hosted-embedder ingest ships the body to Voyage. The user would have marked
the note confidential, watched it succeed, and lost the protection to a background job
with no message anywhere. Downgrading is therefore reserved to the explicit
`brain mark-normal`. Regression tests:
`test_reingest_without_the_flag_does_not_downgrade_a_confidential_doc` and
`test_reingest_can_escalate_a_normal_doc_to_confidential`. **Verified through the real
CLI**: marked a doc confidential, edited the file, re-ingested with no flag → body
updated, tier preserved.

### 2.2 `brain mark-confidential` / `mark-normal` / `list --sensitivity` — `src/brain/cli_docs.py` (owner: `w2b`)

> **⚠️ CORRECTION — the patch originally published here was WRONG. Do not use it.**
> It called `regenerate_vault_file(...)`, which **refuses `kind='vault'` outright**
> (`ValueError: cannot regenerate vault-tier authored note from DB; restore from
> backup or git instead`), so `brain mark-confidential` exited 1 on every authored
> note. I wrote it from the `_set_draft` precedent without verifying that function
> accepts vault-tier rows — the same guess-instead-of-read mistake as `walked.path`.
> w2b found and fixed it; the corrected shape is below.

`queries.set_document_sensitivity()` and `list_documents(sensitivity=)` are already
implemented and tested; this is the thin CLI adapter only.

**The tier branch is mandatory, not a nicety.** Because `sync._sensitivity_from_frontmatter`
makes frontmatter authoritative for vault-tier notes, a DB-only mark is reverted by the
next `vault sync --watch` pass:

```
mark-confidential → sensitivity = 'confidential'
sync_vault(...)   → sensitivity = 'normal'     ← silently downgraded
```

So the command must write the **file** for vault-tier notes and the **mirror** for
ingested-tier ones:

```python
def _set_sensitivity(id_prefix: str, *, level: str) -> None:
    cfg = Config.load()
    with connect(cfg.database_url) as conn:
        conn.autocommit = True
        doc_id = _resolve_id(conn, id_prefix)
        changed = set_document_sensitivity(conn, document_id=doc_id, level=level)
        if not changed:
            typer.echo(f"{id_prefix} is already {level}")
            return
        # Pre-check `kind` from the DB rather than catching + string-matching
        # regenerate_vault_file's ValueError — the message can be rephrased
        # without notice, and pre-checking is what vault/sync.py already does.
        row = conn.execute(
            "SELECT kind, vault_path FROM documents WHERE id = %s", (doc_id,)
        ).fetchone()
        kind, vault_path = row
        if kind == "vault" and vault_path:
            rewrite_sensitivity(cfg.vault_path / vault_path, level)
        elif vault_path:
            regenerate_vault_file(conn, doc_id, vault_path=cfg.vault_path, force=True)
    typer.echo(f"marked {id_prefix} as {level}")
```

#### Where the vault-tier writeback belongs (the view you asked for)

**`vault/frontmatter.py`, as w2b did with `rewrite_sensitivity` — not `_MIRROR_FRONTMATTER_FIELDS`,
and not `cli_docs.py`.** Three reasons:

1. **`_MIRROR_FRONTMATTER_FIELDS` is the wrong mechanism by definition.** It drives
   *mirror regeneration* — rendering an `_ingested/` file from the DB, which is why
   `regenerate_vault_file` refuses vault-tier notes at all. A vault-tier note is not a
   mirror; there is no DB-authoritative body to re-render from, and routing through that
   machinery is what produced the original bug.
2. **`rewrite_sensitivity` is a surgical single-field edit, and there is already a
   sibling for it.** `rewrite_tags` establishes the contract — atomic write, idempotent,
   touches one frontmatter key and leaves the body byte-identical. Sensitivity wants
   exactly that, and having the two live side by side means the next such field is
   obvious rather than inventive.
3. **`cli_docs.py` is the wrong layer.** Frontmatter serialization lives in
   `vault/frontmatter.py`; a CLI module reaching in to hand-edit YAML would put a second
   writer of the on-disk format outside the module that owns it — the same
   two-sources-of-truth shape as the export/sync registry split, which needed a parity
   test to keep honest.

**The general lesson, which is worth recording because it cost two bugs:** the
escalate-only ratchet governs the *re-ingest* path and the file wins on the *vault-sync*
path — so anything setting the tier **from outside the file** falls between the two and
is governed by neither. `mark-confidential` was the first such caller; any future one
(an MCP tool, the `brain ui` toggle) has the same obligation. That gap is invisible from
inside either decision, which is exactly why it survived review.

- `set_document_sensitivity` returns `True` iff the row changed (its
  `WHERE sensitivity <> %s` guard), which is what makes the idempotent
  `"<id> is already <level>"` message truthful with no second round-trip.
- It **already includes `updated_at=NOW()`** — the cross-wave obligation from Task 2A.
  The required test is `test_set_sensitivity_bumps_updated_at`.
- `brain list --json` gains one additive key per row, always present, always a string:
  `"sensitivity": "normal"|"confidential"`. `list_documents` already selects and
  returns it on `DocumentRow`.

### 2.3 Vault frontmatter round-trip — ✅ **DONE** (was: unclaimed; coordinator assigned it to me)

Landed as one batch. The design below is what shipped; kept for reference.

**One decision to be aware of: sync applies a TIER SPLIT**, mirroring `_build_metadata`'s.
Vault-tier notes are file-authoritative (deleting the `sensitivity:` line returns the
note to `normal` — a deliberate edit of the user's own note). **Ingested-tier mirrors are
IGNORED** for sensitivity: `_ingested/` files are *generated* and can legitimately be
stale (written before the tier changed, restored from a backup, hand-copied). Honouring
one would let a routine `vault sync --watch` pass silently downgrade a confidential
document — the same egress hole the escalate-only rule closes on the re-ingest path,
reached by a different route. Regression test:
`test_stale_ingested_mirror_cannot_downgrade_the_column`.

```python
# vault/export.py — _DocumentForExport gains `sensitivity: str = "normal"`,
# the SELECT gains d.sensitivity, and beside the `draft` line in _build_frontmatter:
    if doc.sensitivity != "normal":
        fields["sensitivity"] = doc.sensitivity

# ...and "sensitivity" is added to _EXPORT_OWNED_FRONTMATTER_KEYS.

# vault/sync.py — "sensitivity" is added to the `reserved` set, and the vault-tier
# upsert writes it with a COERCING read:
    level = normalize_level(fm.get("sensitivity"), strict=False)
    if fm.get("sensitivity") not in (None, "", level):
        _logger.warning("note %s has invalid sensitivity %r — coerced to %r",
                        path, fm.get("sensitivity"), level)
```

**`brain.sensitivity.normalize_level(..., strict=False)` exists for exactly this
caller** and returns `"normal"` for anything unrecognized. It never raises — one
hand-typed typo must not abort a `vault sync --watch` pass over 1,376 files — and it
never coerces *up*, so a typo can cost protection the user intended but can never
fabricate protection they did not.

**The key must go in BOTH registries.** A key in the export strip set but not in sync's
`reserved` set is silently deleted from user files on the next export — the exact
regression documented at `vault/export.py:44-57`. Required guards:
`tests/test_vault_frontmatter_registry_parity.py` (the standing invariant) and
`test_normal_mirror_file_is_byte_identical` (no churn across the existing mirrors,
since `sensitivity:` is emitted only when non-`normal`).

### 2.4 Quartz publish boundary — ✅ **DONE**, and the first attempt was WRONG

> **⚠️ The original fix here was insufficient, and the code comment that described
> it was factually wrong.** Extending `contentIndex.ts`'s drop branch removed the
> index entry and left the body **published**. Corrected below. Recording the error
> because the reasoning that produced it is easy to repeat.

**What a real `npx quartz build` showed** (fixture vault, one `sensitivity: confidential`
note, canary `ZEPHYRQUUX`, overlay actually applied in a throwaway workspace):

| Surface | With only the contentIndex filter |
|---|---|
| `confidential-probe.html` | **PUBLISHED — 39 KB, full body** |
| `index.xml` (RSS feed) | **contains the canary** |
| `tags/ops.html` (tag listing) | **contains the canary** |
| `static/contentIndex.json` | absent (filter worked) |
| `static/contentBodies/*.json` | absent (filter worked) |

**The wrong assumption:** that `draft` is quarantined by the contentIndex filter, so
matching its seam inherited its guarantee. It is not. `draft` is filtered by upstream's
`Plugin.RemoveDrafts()` — a `QuartzFilterPlugin` whose `shouldPublish()` returns false,
which drops the file **before any emitter runs**. That is why the build logs
`Filtered out 1 files` and the draft canary appears nowhere. I inherited draft's *seam*
while assuming I had inherited its *guarantee*.

**The fix:** a new `RemoveConfidential` filter plugin
(`quartz_overrides/quartz/plugins/filters/sensitivity.ts`), registered in the overlaid
`quartz.config.ts` as `filters: [Plugin.RemoveDrafts(), RemoveConfidential()]`.
`shouldPublish` gates **every** emitter at once, so it closes page + RSS + tag pages +
index + bodies without enumerating them — and the enumeration was already wrong once
(nobody listed RSS or tag pages).

**Verified:** rebuilt with the filter → no HTML page for the slug, canary absent from
**all 48 built files**, `tags/ops.html` gone entirely (that tag existed only on the
confidential note, so the auto-tag surface closed too), and normal pages unaffected.

**Design points:**
- **Separate plugin, not a change to `RemoveDrafts`.** It is upstream code, and the two
  flags encode different guarantees — `draft` = "not ready to show", `confidential` =
  "must not leak". Sharing a mechanism is fine; sharing a branch is what let a publish
  guarantee be assumed rather than checked.
- Imported **by path**, not through the `Plugin` barrel, so the overlay does not have to
  replace upstream's `quartz/plugins/filters/index.ts`.
- **Quartz-level, not export-level** — and this is forced, not preferred:
  `brain wiki` builds with `--directory <cfg.vault_path>` (`cli.py:6246`, `:6261`), so
  **the publish source IS the user's live vault**. Stripping confidential bodies at
  export would delete them from the vault the user reads in Obsidian. Publish nothing,
  keep everything locally.
- The `contentIndex.ts` branch is now **redundant** (the filter drops the file before
  that emitter runs) and is deliberately **kept as defence-in-depth**, with a comment
  saying so, in case the filter is ever removed or reordered.

**Tests:** `tests/test_quartz_confidential_filter.py` — static checks that the plugin
exists **and is registered** (registration is the half that silently rots), plus an
`e2e`-marked real `npx quartz build` that greps the **entire** output tree rather than
the files it expects to be risky. **Red-green proven:** with the filter unregistered the
e2e test fails; with it registered it passes.

## 3b. Secret guard inside `vault sync` — fixed (was: one file could kill a walk)

`SecretGuardError` was caught **nowhere** in `vault/sync.py` or `vault/watch.py`, and the
guard was not wired into sync at all. Both are now addressed together, because handling
alone is untestable (nothing raises) and wiring alone is unsafe.

- `_guard_synced_body()` converts `SecretGuardError` → the existing `_SyncError` seam, so
  **both** per-file handlers (`sync_vault`'s walk loop at `:193`, `sync_one_file`) record
  it and continue. Previously a `reject`-mode refusal propagated out of `sync_vault` and
  aborted the whole walk.
- `SyncReport.secrets_refused` counts refusals separately from `errors` (where they also
  appear): a refusal is a deliberate policy outcome, not a malfunction.
- **The `report.errors` message is rebuilt, not reused.** `SecretGuardError`'s text is the
  multi-line CLI block including finding previews; `report.errors` is rendered into logs
  and terminals by callers, so echoing previews there would spread the credential beyond
  the file it came from.
- Guard runs **before** `_normalized_body` feeds the content hash — same load-bearing
  ordering as the ingest pipeline, for the same reason (a hash describing un-redacted text
  while storing redacted text makes the next sync a false no-op).
- `secret_guard` defaults to **`"off"`**, not `DEFAULT_SECRET_GUARD`, so all seven existing
  call sites (`cli.py` ×4, `mcp_server.py` ×2, watcher) are behaviourally identical until
  a caller opts in by passing `cfg.secret_guard`.

**`redact` on a vault-tier note REFUSES rather than applying.** Storing a redacted body
while the user's file keeps the secret makes the two disagree, and because vault-tier
files are file-authoritative the file wins on the next pass — the redaction silently
evaporates *after reporting success*. Sync's remit is mirroring file→DB; rewriting a
user's authored prose is a categorically larger act than rewriting one generated
frontmatter field. Refusal is loud, lossless, reversible — the reasoning that makes
`warn` the guard's default. Ingested-tier bodies are generated, so redaction there is
coherent and applies normally.

**Correction to a diagnosis in circulation:** the `--watch` daemon was never at risk.
`watch.py:819` has a broad `except Exception` that increments `state.errors` and logs, and
the worker's docstring states it is self-healing. The defect there was the *quality* of
the failure — a stack trace logged as an unexpected error with nothing in
`report.errors` — not availability. The bulk-walk abort was the real availability bug.

Tests: `tests/test_vault_sync_secret_guard.py` (9). The headline one asserts the file
**after** the refusal still syncs — asserting only the recorded error would pass even if
the walk aborted immediately after recording it.

## 3c. Task #23 — duplicate titles crashed ingest and left invisible orphans

**Root cause was narrower than reported.** `_ingested_relative_path` already had
correct, deterministic collision handling (append `_short_id(doc.id)`). The bug was
that the **single-document** path passed an empty `set()` as its collision oracle
(`export.py:706`), so the check could never see a path an existing row already owned.
PostgreSQL's `documents_vault_path_idx` raised instead, as a raw traceback.

**The oracle question is the transferable lesson.** `note_builder._unique_target` checks
the **filesystem** (`target.exists()`); the constraint that actually rejects is a **DB
unique index**. A row can own a `vault_path` whose file is missing — exactly the orphan
state this bug produced — so the filesystem was never the right authority. The fix
injects the oracle: `_ingested_relative_path` / `_resolve_relative_path` now take an
`is_taken: Callable[[str], bool]`; the corpus dump passes its in-run
`used_paths.__contains__`, the single-document path passes
`_paths_taken_by_others(conn, document_id)`.

**Corrections to the escalation, measured:**
- *"No amount of re-running ever fixes it"* — **not true of the intended repair path.**
  `brain vault export --force` **then** `brain vault sync` fully closed the orphan
  before any fix. So the deliberate out-of-transaction design's premise ("prefer
  recoverable drift; `brain vault export` reconciles it") **held**. Re-running
  `brain ingest` was the only thing that never helped.
- Worth its own note: `export --force` writes the **file** but does **not** write
  `vault_path` back to the DB. Repair takes export **then** sync.
- The genuine defect was therefore the **silent success**, not data loss: the retry said
  `skipped (already ingested)` at exit 0, so the user was told everything was fine.

**Deliberately NOT done: making the vault write share the row's transaction.** That
would reverse a documented decision and let a filesystem error (full disk, permissions)
abort an otherwise-valid ingest — trading recoverable drift for lost work. Coordinator
agreed. The three landed changes fix the real defect without weakening ingest:

1. **Prevention** — DB-backed collision oracle (above), plus a second suffix widening to
   the full uuid if the 8-hex short id itself collides.
2. **No raw traceback** — `ingest_document` catches `psycopg.errors.UniqueViolation`
   alongside `OSError` and degrades to the existing warning. Belt-and-braces now that (1)
   should make it unreachable. `regenerate_vault_file`'s `ValueError` paths stay
   **uncaught** — both are impossible for a freshly-inserted `kind='ingested'` row, so
   catching them would mask unrelated bugs.
3. **Recovery** — `_vault_path_missing()` treats a row with no recorded mirror as
   "mirror still owed", so a re-run repairs it. Keyed off the **outcome**, not the cause,
   so it also covers a future post-commit failure of any kind. `IngestResult.mirror_repaired`
   reports it, because a bare `skipped` on a run that did real work understates it —
   the same failure class as the silent success.

**Verified end to end on a scratch DB:** before, `dup2` → exit 1 + traceback + orphan;
after, both ingest at **exit 0** with `duplicate-title-qa.md` and
`duplicate-title-qa-16c1f26d.md`, **zero orphans**. A pre-existing orphan was repaired by
a plain re-run. Tests: `tests/test_ingest_duplicate_titles.py` (6).

**⚠️ ONE CLI LINE STILL OWED, for whoever owns `cli_ingest.py`:** `_ingest_outcome_verb`
still returns `"skipped (already ingested)"` on a repair run. `IngestResult.mirror_repaired`
is populated for exactly this; the verb should acknowledge the repair (e.g.
`"repaired mirror"`). Not done here to avoid cross-editing a file another agent holds.

## 3c-bis. ⚠️ `brain doctor`'s orphan remedy is WRONG — coordinator patch for `cli.py`

**Task #23 item 4.** `brain doctor` *does* surface `NULL vault_path` rows
(`mirror_drift_summary` already counts them, `cli.py:2032` prints a remedy). The problem
is that **the remedy it prints does not work**.

It says:
```
— `brain vault export --force` to populate NULL vault_path
```

Measured on a clean scratch DB, running exactly that:
```
orphans before:                    1
brain vault export --force  →  "wrote 0 file(s), skipped 1"
orphans after doctor's remedy:     1        ← no-op
brain vault sync            →
orphans after export+sync:         0        ← the command doctor never names
```

**Why `export --force` is a no-op here, not merely insufficient.** Export skips a file
whose on-disk content hash already matches the row. In the common orphan shape — the file
was written, then the `vault_path` write-back failed or was lost — the file is already
correct, so export writes nothing and never touches the column. Export does not write
`vault_path` back at all; only `vault sync` (file → DB) sets it.

So a user follows the instruction, sees `wrote 0 file(s)`, re-runs `brain doctor`, sees
the identical drift, and has no path forward. **A remedy that reports success while
changing nothing is the same failure class as #23's `skipped (already ingested)`.**

**Exact patch — `cli.py` is coordinator-only, so I have not applied it:**

```python
# src/brain/cli.py, in the vault-drift doctor check (~line 2032):
     if summary.rows_with_null_vault_path:
         lines.append(
             _DoctorLine(
-                "                — `brain vault export --force` to populate "
-                "NULL vault_path",
+                "                — `brain vault export --force` then "
+                "`brain vault sync` to repair NULL vault_path (BOTH: export "
+                "writes the file, sync writes the path back)",
                 fg="yellow",
             )
         )
-        remedies.append("`brain vault export --force` to populate NULL vault_path")
+        remedies.append(
+            "`brain vault export --force` then `brain vault sync` to repair "
+            "NULL vault_path (both commands: export writes the file, sync "
+            "writes the path back)"
+        )
```

The parenthetical is deliberate: without it the two-command sequence looks like
belt-and-braces, and a user who sees `wrote 0 file(s)` from the first will reasonably stop
there.

**Note this is now a rare path**, since #23's fix prevents the collision that produced
orphans and a re-ingest repairs any that already exist. But the remedy should be correct
for the orphan shapes that can still arise from any other post-commit failure.

## 4a. Task #14 — tsquery double-stemming: `facets.py` FIXED; one instance REMAINS

`build_tsquery` returns **lexemes** (already through `plainto_tsquery`). Binding them as
`to_tsquery('english', %s)` stems them a second time and they stop matching the stored
`tsv`. Measured read-only on the live 1,376-doc corpus: **2.5%** of the top-2000
single-token lexemes are affected (46/1833), including `databas`, `respons`, `decis`,
`convers`, `releas`, `enterpris`.

**Fixed here:** `facets.py` — both `_TOTAL_COUNT_SQL` and `_FACET_SQL` now bind
`%s::tsquery`. This was the surviving half: `search.py`'s ranked legs and the
`graph_rag` legs had already been corrected, but the count/facet legs had not, so the
two **disagreed**. On production, `provisioning` matched **94 documents** in the ranked
leg and **1** in the facet leg — a footer reading `1 matched` above a screen of results,
authoritative and wrong by two orders of magnitude. `facets.py` exists specifically to
stop the total and the panel drifting from the results they annotate, so it is the one
module where a divergent binding is least acceptable.

**Canaries: no movement to adjudicate.** `test_search_canary_queries.py` +
`test_search_floor_default_excludes_known_bad.py` → **7 passed** against the live
corpus. That is expected rather than lucky: this change touches only the count/facet
legs, never ranking, so no canary *could* legitimately move. A movement here would have
indicated an unintended ranking change.

**STILL BROKEN — not my file: `src/brain/wiki/build_related.py`.**
`_top_body_lexemes` pulls lexemes via `ts_stat` over `chunks.tsv` (already stemmed), and
`:674` re-parses each one with `to_tsquery('english', %s)` before they are fed to
`:367/:374/:379`. Same bug class.

**Severity is LOWER than the search case and should be triaged accordingly:** those
lexemes are `" | ".join`-ed (OR, not AND), so an affected term contributes nothing
instead of zeroing the whole query. The effect is *degraded* Related-Docs relevance —
roughly the same 2.5% of each document's top lexemes silently stop contributing — not
empty results. Fix is the same one-line shape (`%s::tsquery`), but it changes
Related-Docs output and so wants its own before/after comparison.

**Regression test:** `tests/test_tsquery_stem_stability.py`, deliberately built on
**unstable** terms (`provisioning`, `responsive`, `decision`, `conversation`). It opens
with `test_the_chosen_terms_really_are_unstable`, a guard-on-the-guard: if a future
Postgres/Snowball change made those terms stable, every other test in the module would
still pass while testing nothing — which is exactly how the original bug survived. My
own first workaround during F6 was to switch a test's vocabulary to stem-stable words,
the same blind spot.

## 4b. Migration-order tripwire generalized — **w2b's 027 needs no test edit**

`tests/test_migrations_apply_in_any_order.py` used to assert the head migration by
literal filename (`025_documents_updated_at.sql`). It fired exactly as designed when
026 landed. It is now **generalized**, so adding 027 will NOT trip it:

```python
unpadded = [n for n in applied if not re.match(r"^\d{3}_", n)]
assert not unpadded
numbers = [int(n.split("_", 1)[0]) for n in applied]
assert numbers == sorted(numbers)              # lexicographic == numeric
assert applied[-1] == max(applied, key=_numeric_prefix)
```

Naming a file pinned the wrong invariant. `run_migrations` applies
`sorted(glob("*.sql"))` — a **lexicographic** sort — and what matters is that it agrees
with the numeric intent of the filenames. That holds only while every prefix has the
same digit width.

**Correction to an earlier draft of this document:** it claimed the ordering broke at
migration 100. That is wrong — `'026_y.sql' < '100_x.sql'` because `'0' < '1'`, so 100
sorts correctly. The width change happens at **1000** (`'1000_x.sql' < '999_y.sql'`
because `'1' < '9'`). Verified:

```
sorted(['100_x.sql','026_y.sql'])  -> ['026_y.sql', '100_x.sql']   # fine
sorted(['1000_x.sql','999_y.sql']) -> ['1000_x.sql', '999_y.sql']  # breaks
sorted(['026_a.sql','26_b.sql'])   -> ['026_a.sql', '26_b.sql']    # un-padded sorts LAST
```

The third line is why the padding assertion earns its place: an un-padded `26_foo.sql`
is a *live* risk today and would silently reorder the set on the next fresh install,
whereas migration 1000 is ~974 away.

`test_025_applies_cleanly_when_it_lands_last` is deliberately **left naming 025** — it
is a historical schema-fingerprint guard for that specific migration, not an ordering
tripwire, and generalizing it would destroy its point.
