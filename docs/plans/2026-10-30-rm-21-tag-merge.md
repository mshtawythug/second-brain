## Design, as built

- **The loop** (`run_mapping`) runs in autocommit. For each document whose mapped,
  `normalize_tags`-ed tags differ, it does three things: `UPDATE documents SET tags`,
  `sync_chunk_search_metadata`, and `rewrite_tags` on the file at `vault_path`. There is no single
  transaction (RM-21.D2), and `updated_at` is not bumped.
- **rename / merge** build `{old: new}` (`build_rename_mapping`, `build_merge_mapping`) and run
  the loop with `only_mapped=True`. They then call `rewrite_watch_filters`. Each saved search
  whose `tag` / `without_tag` names a mapped tag is updated with one `UPDATE` guarded on the
  filters it read, and other keys are kept. Dry run by default; `--apply` writes.
- **suggest-merges** finds three kinds of pair:
  - `SequenceMatcher` ratio ≥ 0.85, with length and quick-ratio pruning;
  - singular/plural (`ies`→`y`, `es` after a sibilant, `s` but not `ss`);
  - co-occurrence: Jaccard (shared / |A∪B|) ≥ 0.8, computed in one pass, on ≥ 2 shared documents; `jaccard` supplies the overlap evidence.

  Suggestions are ranked by number of reasons, then by max(ratio, overlap), then by use. Each
  carries counts, ratio, overlap and the number of shared documents. `keep` is the more used tag.
- **MCP** is read-only by decision (RM-21.D1), enforced by a `READ ONLY` transaction, with the
  F6 lens in the SQL predicate.

## Deviations

1. **Co-occurrence also needs at least 2 shared documents.** The ticket sets Jaccard ≥ 0.8. On its own that suggests every pair of tags that each appear once, on the same document (overlap 1.0), which floods the list. `tag_mapping.MIN_SHARED_DOCS = 2` is added. The mutation that drops it is killed.
2. **The MCP tools take `include_confidential` and a bounded `limit`, and run in a `READ ONLY` transaction.** The ticket names the two tools only. The `mcp_tools` seam requires the F6 lens on every tool that returns corpus-derived data, and a tag's name and count are. So the lens is in the SQL predicate, excluding confidential documents by default. `limit` is 1–1000 for `brain_tags_list` (default 200) and 1–100 for `brain_tags_suggest_merges` (default 25). Both tools are added to `_KNOWN_GATED` in `tests/test_mcp_confidential_discovery_gate.py`.
3. **`suggest-merges` takes `--limit` (default 50) and `--json`.** The ticket specifies `--json` for `list` only.
4. **`merge` takes one or more sources, and `--into` may be one of them.** `--into` is dropped from the mapping. The ticket's example has two sources.
5. **`rename` and `merge` touch only documents that carry a mapped tag** (`run_mapping(only_mapped=True)`). A document that carries no mapped tag is not touched, even if its tags are non-canonical (that is `brain backfill normalize-tags`' job). A document that does carry one has all of its tags normalized, as normalize-tags would.
6. **`brain backfill normalize-tags` does not rewrite saved searches.** The ticket asks for the saved-search rewrite on rename and merge. normalize-tags' success-path output is unchanged (AC4); its one change is Deviation 7. `add_watch` already stores saved-search filters normalized.
7. **A file that cannot be rewritten is a per-document failure, in `brain backfill normalize-tags` too.** This was added in review round 1. An unreadable file, bad frontmatter or a `vault_path` outside the vault used to abort the whole run, and a re-run then skipped the stale file as already done. Each such file is now counted in `MappingReport.files_failed` and reported by exception class only (`describe_failure`). The summary adds `, N file(s) failed`, and the command exits 1 after finishing everything else. This lives in the loop both commands share, so normalize-tags gains it as well. Its success-path output is still byte-identical (the AC4 golden); the summary clause appears only when a file failed.
