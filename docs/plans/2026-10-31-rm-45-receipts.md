## Goal

A receipt's PDF or image attachment is searchable together with its email. With
`--with-attachments`, `brain ingest-gmail` downloads each PDF, PNG or JPEG attachment of at most
10 MiB through `gws`, extracts its text through `ingest.dispatch` (the PDF text layer, or RM-32's
OCR), and appends it to the thread document as an `## Attachment: <name>` section. The kind stays
`gmail`, the content type stays `email_thread`, and the dedup rule stays the Gmail thread rule.
Attachments are never separate documents (RM-45.D1, so RM-60 stays unbuilt).

## Hard constraints for this ticket (restated for every teammate brief)

- Never read the owner's real mail, receipts, downloads or accounts. Never run the real `gws`
  against an account: every test injects the runner, and the e2e puts a synthetic `gws` shim first
  on `PATH` and checks that `command -v gws` resolves to it before running anything. No real
  network. Don't search `~/Downloads`, `~/Documents`, `~/Library`, the mail stores, `/` or `$HOME`.
- Fixtures are synthetic and built from named constants: merchants such as `Example Hardware
  Co.`, addresses at `example.com`, the street `1 Example Way`, and card digits that are either
  the documented test PAN `4111 1111 1111 1111` or obviously fake masks (`**** 0000`). PDFs are
  built with `reportlab` (already a dev dependency) and images with Pillow, in `tmp_path` or the
  scratch directory.
- Test DB `second_brain_test_rm45` on 5434 only. Never 55432, `~/brain-vault` or `data/postgres`.
  The e2e runs the worktree's interpreter (`python -m brain`), never the installed `brain`.
- Attachments are hostile input from the first line of code (threat model below). Anyone can mail
  the owner a PDF, and a Gmail filter can put it under the receipts label.
- No logging in the new modules (counts are printed by the CLI layer). Exception classes end in
  `Error` and are never stored on an attribute. Errors carry fixed messages, never attachment
  text or names; caught errors print through `describe_failure`.

## What was checked first (protocol point 4)

The ticket asks whether the installed `gws` exposes `attachments get`. Evidence, gathered without
contacting any account and without network:

- `/opt/homebrew/bin/gws` → `googleworkspace-cli` 0.22.5. It builds its command tree from Google's
  public Discovery documents and caches them.
- The cached public Gmail Discovery document (`gmail_v1`, revision `20261026`) has
  `users.messages.attachments.get`: `GET gmail/v1/users/{userId}/messages/{messageId}/attachments/{id}`,
  parameters `userId`, `messageId`, `id`, accepted under the `gmail.readonly` scope (the same scope
  as `messages.get`). Its response is `MessagePartBody`: `attachmentId`, `size`, `data` (base64url).
- So the call is `gws gmail users messages attachments get --params
  '{"userId":"me","messageId":"<m>","id":"<a>"}' --format json`, the same shape as the
  `messages get` call `gmail.py` already makes.

I did **not** run `gws gmail users messages attachments --help`, because the CLI may refresh the
Discovery document over the network when it does (D1).

## Input: what is read and how it is bounded

The source is the Gmail `Message` resources that `read_thread_messages` already fetches
(`format=full`), so there is no extra listing call. Per kept message (`rendered_messages`):

1. **The MIME walk.** Iterative, never recursive: at most `MAX_MIME_DEPTH = 32` levels and
   `MAX_PARTS_PER_MESSAGE = 500` parts. Past either cap the message's remaining parts are not
   considered, and the thread counts one `malformed`. A part that is not a mapping, or whose
   `parts` is not a list, is skipped.
2. **The prefilter** (before any download). A part qualifies when its `filename` is a non-empty
   string and either its declared `mimeType` is one of `application/pdf`, `image/png`,
   `image/jpeg`, `image/jpg`, or it is `application/octet-stream` and the filename ends in `.pdf`,
   `.png`, `.jpg` or `.jpeg`. An image part that is inline (`Content-Disposition: inline`, or a
   `Content-ID` header: a logo referenced from the HTML body) does not qualify (D9). Everything
   else is ignored silently: this is "non-PDF, non-image" scope-out, not a failure.
3. **The declared size.** `body.size` must be a non-negative `int` (not a `bool`). Over
   `MAX_ATTACHMENT_BYTES = 10 MiB` the part is skipped **without being fetched** and counted
   `too large` (acceptance 2).
4. **The run cap.** At most `MAX_ATTACHMENTS_PER_RUN = 50` parts are processed per run (fetched,
   or decoded from inline data). The 51st and later are counted `over cap` and not fetched
   (acceptance 5). A run deadline of `ATTACHMENT_RUN_DEADLINE_S = 900` s (monotonic clock, a test
   seam) is checked before each fetch; past it, the rest are counted `deadline`.
5. **The fetch.** `messageId` and `attachmentId` must match `^[A-Za-z0-9_-]{1,1024}$` before they
   enter the `--params` JSON (no shell is involved; this rejects junk early). The runner is
   `real_gws_runner(argv, timeout=60, max_stdout_bytes=GWS_MAX_STDOUT_BYTES)` with
   `GWS_MAX_STDOUT_BYTES = 4 * ceil(10 MiB / 3) + 64 KiB` (the base64 of a 10 MiB part plus the
   JSON around it). Oversized stdout is refused while it is read; the process group is killed.
6. **The response.** At most `GWS_MAX_STDOUT_BYTES` bytes reach `json.loads`; a `RecursionError`
   or `ValueError` is `malformed`. The top level must be an object whose `data` is a `str`; other
   keys are ignored.
7. **The decode.** `data` (inline or fetched) must match `^[A-Za-z0-9_-]*={0,2}$` and be at most
   `4 * ceil(MAX_ATTACHMENT_BYTES / 3)` characters long **before** decoding; the decoded length is
   checked again (`too large` if over). A declared size that disagrees with the decoded size does
   not matter: only the decoded size is trusted.
8. **The type.** Magic bytes decide (D11): `%PDF-` at offset 0, the 8-byte PNG signature, or
   `FF D8 FF`. No match is `unsupported`, whatever the declared type said. The temp file's suffix
   comes from the sniffed type, so the registry routes on what the bytes are.
9. **The extraction.** A private directory from `tempfile.mkdtemp(prefix="brain-gmail-att-")`
   (mode 0700), created once per run and removed in `finally`; `sweep_stale_tempdirs` with the
   same prefix runs at start. Each attachment is written to a fixed name (`attachment.pdf`,
   `.png` or `.jpg`; the sender's filename never touches the filesystem) with
   `O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW`, mode 0600, and unlinked after extraction, also on
   error. For a PDF, a pre-check with `pypdf.PdfReader` (imported inside the function, so the
   base CLI stays light) refuses an encrypted file (`encrypted`) or one with more than
   `MAX_ATTACHMENT_PAGES = 50` pages (`too many pages`) before `extract_pdf` runs. Then
   `dispatch.extract_path(path)`: RM-32's PDF bounds (image pre-scan, page bitmap caps, the 600 s
   OCR deadline) and RM-33's image bounds (`O_NOFOLLOW`, decoder whitelist, pixel caps, grayscale
   re-encode before tesseract) apply unchanged. An image with OCR off or no `tesseract` is
   `OcrUnavailableError`: counted `unreadable`, and the hint printed once per run.
10. **The text.** Per attachment: card numbers redacted (D8), markup neutralized (D15), capped at
    `MAX_SECTION_CHARS = 50_000` with a fixed `[attachment text truncated]` line. Per thread, all
    sections together are capped at `MAX_THREAD_ATTACHMENT_CHARS = 200_000`; past it, the remaining
    attachments are counted `truncated` and not extracted. Empty text is counted `empty` and
    gets no section.

Statuses: `extracted`, `empty`, `too large`, `too many pages`, `encrypted`, `unsupported`,
`unreadable`, `malformed`, `failed` (a `gws` error), `over cap`, `deadline`, `truncated`. The
run ends with one line, for example `attachments: 3 extracted, 1 too large, 0 failed, 2 over
cap`. Zero counts other than `extracted` and `failed` are left out.

## The document model

The thread document is built exactly as today (`to_extracted_thread`), then
`attachment_text.with_sections` returns a new `ExtractedDoc` whose content is the thread body
followed by one section per extracted attachment, in message order:

```markdown
## Attachment: Receipt-0001.pdf

Example Hardware Co.
1 Example Way, Exampleville
Card [REDACTED:card-number]
Total 12.34
```

`metadata` gains two keys:

- `attachments`: one record per qualifying part, `{"message_id", "part_id", "type", "bytes",
  "status"}` plus `"pages"` and `"ocr"` when known. **No filename** (D14): metadata is not
  scanned by the secret guard.
- `attachments_fingerprint`: SHA-256 over the mail-only body, the sorted
  `(message_id, part_id, declared size)` keys of the candidates, and a constant
  `ATTACHMENT_POLICY_VERSION = "v1"` (bumped when extraction or text rules change, so a re-run
  re-extracts).

The key is `part_id`, not `attachmentId`: Gmail's attachment ids are not stable across
`messages.get` calls, while a message's part ids are.

`content_type` stays `email_thread`; the chunker, FTS, the vault mirror and the UI need no change.

## Dedup and re-runs (protocol point 3)

The dedup key is the Gmail thread (`thread_id`, `email_thread`), unchanged. Three re-run cases:

1. **Same flag, nothing new.** Before fetching anything, the stored document's
   `attachments_fingerprint` (read with `volatile_patch.stored_document(conn, "gmail", tid)`) is
   compared with the fingerprint of the messages just read. When they match and every stored
   record has a final status (not `failed`, `over cap`, `deadline`, `unreadable` or `truncated`),
   the thread is reported `skipped (unchanged)` with **no attachment download**, no
   `ingest_document` call, and only the sensitivity rule below (D7). A test pins the runner's call
   count.
2. **Same flag, a new reply or a retryable status.** The attachments are fetched again (within the
   run cap), and the new body updates the row in place; the UUID is kept (the existing P2.2
   path).
3. **A plain run (no flag) over a thread stored with attachments.** Without a guard, the plain run
   would rebuild the body from the mail alone and silently drop the receipt text. So the plain run
   skips such a thread (a stored `attachments` key) and prints `skipped thread <tid> (has
   attachments: re-run with --with-attachments)` (D6). One `SELECT` per thread; a thread not yet
   stored costs nothing extra.

## Sensitivity and PII (protocol point 6)

- **Default.** With `--with-attachments`, every thread the run writes is `confidential`
  (acceptance 4, D4): a new thread is inserted `confidential`; a changed thread is escalated by
  `ingest_document`'s escalate-only update path; an unchanged (skipped) thread is escalated through
  `cli_sensitivity_rerun.escalate_stored_sensitivity(..., level=CONFIDENTIAL, explicit=True)`,
  which also re-fences the vault mirror. Nothing ever lowers a tier; `brain mark-normal` is the
  only way down. Without the flag nothing changes. No `--sensitivity` option is added (D5).
- **What `confidential` buys.** The hosted-embedder egress veto (a `voyage` setup stores the text
  and FTS-indexes it, with no vectors), the vault mirror's confidential handling, and the F6
  filters on browsable reads.
- **What is stored.** The extracted attachment text, card numbers redacted; the sanitized
  filename in the section heading only; the per-part record above (ids, sniffed type, byte count,
  pages, status).
- **What is dropped or redacted.** The attachment bytes (never stored; the temp file is unlinked);
  card numbers (13 to 19 digits, single spaces or hyphens allowed between digits, passing the Luhn
  check) become `[REDACTED:card-number]` (D8); filenames never reach metadata, logs or the
  terminal (D14); the image's EXIF is never read (RM-33 re-encodes). Masked forms such as
  `**** 0000` are kept: they identify which card without being a card number.
- **The secret guard** runs on the whole thread content, sections included, through
  `ingest_document` (`BRAIN_SECRET_GUARD`); `--allow-secrets` keeps its current meaning. A
  `reject` refuses the thread as today, per thread. The title is the email subject, unchanged by
  this ticket (BL-38 is not widened: attachment names never become titles).
- **Addresses and order numbers** in the text are kept: they are what a receipt search needs, and
  the document is confidential.

## Security threat model (hostile inputs)

| # | Threat | Defence | Test |
|---|---|---|---|
| T1 | Decompression bomb in a PDF stream | pypdf's per-stream output cap (75 MB, pypdf ≥ 6.14 floor), the 50-page pre-check, RM-32's image pre-scan before pdfium opens it, the per-section and per-thread text caps | a reportlab PDF over the page cap; a monkeypatched small cap |
| T2 | Image decompression bomb (huge declared dimensions in a small PNG) | RM-33: decoder whitelist, header pixel cap, Pillow's bomb check | a synthetic PNG header declaring 100k × 100k |
| T3 | Oversized download (lying `size`, then a 1 GB answer) | declared-size pre-check; stdout cap in the runner (kills the group); base64 length check before decode; decoded length check after | fake runner returning more than the cap; declared small, decoded big |
| T4 | JSON structural amplification or deep nesting in the `gws` answer | the stdout cap bounds the input; `RecursionError` and `ValueError` are caught as `malformed`; only `data` is read | 100k nested arrays within the cap |
| T5 | Deep or wide MIME trees (`multipart` bombs) in the message | iterative walk, depth 32, 500 parts per message | `nested_multipart(10_000)`; 5,000 sibling parts |
| T6 | Type confusion (an HTML or SVG renamed `.pdf`, a polyglot) | magic bytes decide; the suffix comes from the sniff; only PDF, PNG and JPEG extractors are reachable | `.pdf` holding HTML is `unsupported`; a PNG named `.pdf` goes to the image extractor |
| T7 | Path traversal or symlink via the filename (`../../.ssh/x`, `/etc/passwd`) | the filename never touches the filesystem; fixed temp names; `O_EXCL | O_NOFOLLOW`; a private 0700 directory | a hostile filename; the temp dir's mode and emptiness after a run |
| T8 | Markup or heading spoofing in the name or text (`</details>`, `<summary>`, a fake `## 2026-… — boss@example.com` heading, terminal escapes, bidi overrides) | `one_line` and category-`C` removal; `html.escape(quote=False)`; `\#` on leading `#`; name capped at 120 characters | rendered through `ui.render.render_markdown`: no extra `<details>` block, no extra H2 |
| T9 | Secrets in attachment text or name | the guard runs on the full body; names stay out of metadata and the terminal | guard `redact` and `reject` over a synthetic token in a PDF |
| T10 | Card numbers | Luhn-checked redaction before the section is built | test PAN redacted; 16-digit non-Luhn order number kept; masked `**** 0000` kept |
| T11 | Slow or hanging `gws` | 60 s timeout per call (the process group is killed); the run deadline | fake runner raising the timeout error |
| T12 | Slow parse or OCR (CPU exhaustion) | page cap, RM-32's 600 s per-document OCR deadline, the 900 s run deadline before each new attachment, the 50-per-run cap | fake clock past the deadline |
| T13 | Encrypted PDF (password-protected statement) | refused before extraction (`encrypted`) | reportlab with `encrypt=` |
| T14 | Argument injection through ids | id regex; argv list, no shell; values inside the `--params` JSON | an id with `--`, spaces and quotes is `malformed`, and the runner is never called |
| T15 | Error messages leaking content (a parser message quoting text, `gws` stderr quoting the account) | fixed messages; `describe_failure` prints class names only; `run_capped` discards stderr | assert the output holds no fixture text when an extractor raises with content in its message |
| T16 | Unbounded run (a broad query) | `--label` or `--query` required with the flag (acceptance 3); the existing `--max`; the 50-per-run cap | CLI refusal with only `--since`/`--from`; zero runner calls |
| T17 | Temp files left behind (crash, SIGKILL) | `finally` cleanup; `sweep_stale_tempdirs` at start (max age 2 × the run deadline) | an extractor that raises leaves no file |
| T18 | Draft attachments surfacing in a published thread | `rendered_messages` is the one draft rule for body and attachments | a mixed thread whose draft carries a PDF |

What this does not defend against, stated in the PR: a memory-corruption bug in pdfium or a
Pillow C decoder reached by a hostile file. That exposure already exists for owner files (RM-32,
RM-33); here the sender is a third party. Process isolation is D10.

## Open decisions

Each has my recommendation first.

- **D1 — Evidence that `gws` has `attachments get`.** (a) Accept the cached public Discovery
  document (method, path, parameters and scope above) and run no `gws` command at all.
  **Recommended**, since the hard rules forbid running `gws` and `--help` may hit the network.
  (b) Team-lead authorizes one `gws gmail users messages attachments --help`, which contacts no
  account but may fetch the public Discovery document.
- **D2 — Where the I/O lives.** (a) Nothing new in `gmail.py` except the public
  `rendered_messages`; the fetch uses `real_gws_runner` with a 60 s timeout and a stdout cap.
  **Recommended.** Note that the ticket says "the injectable runner `gmail.py` already uses, 60 s
  timeout", but `gmail._run` has **no** timeout and no stdout cap today. Reusing it would leave
  attachment downloads unbounded. (b) Add a timeout and cap to `gmail._run` and use it. That
  changes every existing Gmail call and spends `gmail.py`'s budget; it could be a follow-up.
- **D3 — Module split.** (a) Three modules: the untrusted reader (`ingest/gmail_attachments.py`),
  the pure text rules (`ingest/attachment_text.py`) and the CLI layer
  (`cli_gmail_attachments.py`), with `cli_ingest.py` wiring only. **Recommended** (SRP, and the
  over-ceiling file grows about 12 lines). (b) Everything in `gmail_attachments.py` plus a larger
  `cli_ingest.py` diff.
- **D4 — Which threads become confidential.** (a) Every thread a `--with-attachments` run writes or
  skips as unchanged, including one with no qualifying attachment. **Recommended:** acceptance 4
  read literally, and a receipts-labelled email body carries the same addresses. (b) Only threads
  that gained at least one section.
- **D5 — A `--sensitivity` option on `ingest-gmail`.** (a) None; the flag decides. **Recommended**
  (out of the ticket's scope). (b) Add it with the escalate-only rule.
- **D6 — A plain run over a thread stored with attachments.** (a) Skip it with a hint.
  **Recommended:** the receipt text is never silently dropped. (b) Rebuild it from the mail and drop
  the sections (simplest, but lossy). (c) Carry the stored sections over by parsing the stored
  body (fragile).
- **D7 — Idempotent re-runs.** (a) Fingerprint skip: no download when nothing changed.
  **Recommended.** (b) Re-download every run (bounded by the 50 cap, but slow, and repeated work).
- **D8 — Card numbers.** (a) Always redact Luhn-valid 13–19 digit runs in attachment text,
  whatever `BRAIN_SECRET_GUARD` says. **Recommended.** (b) The same, and also in the email body
  under the flag. (c) No redaction (the secret guard has no card pattern).
- **D9 — Inline images.** (a) Skip images marked inline or carrying a `Content-ID` (logos);
  always take PDFs. **Recommended:** otherwise a single HTML receipt can spend the 50-cap on logos.
  (b) Take every image part.
- **D10 — Extraction isolation.** (a) In-process, with RM-32/RM-33's bounds plus the page cap, the
  encryption refusal, the text caps and the run deadline. **Recommended** for this ticket (the
  same exposure as `brain ingest x.pdf`), with the residual risk stated in the PR. (b) A
  subprocess per attachment under `RLIMIT_AS`, `RLIMIT_CPU` and a timeout (strongest against the
  third-party sender, about +150 lines and a new worker entry point). It could be a follow-up
  backlog row.
- **D11 — Type authority.** (a) Magic bytes decide; the declared type and filename only
  prefilter. **Recommended.** (b) The declared type decides.
- **D12 — The cap values.** 10 MiB and 50 per run (the ticket); 50 pages; 50,000 characters per
  attachment; 200,000 per thread; a 900 s run deadline; MIME depth 32; 500 parts per message;
  names capped at 120 characters. **Recommended as listed.**
- **D13 — `--dry-run` with the flag.** (a) One note line; no attachment work. **Recommended.**
  (b) Count the candidates per thread (it would mean reading each thread's messages twice).
- **D14 — Where filenames go.** (a) Only in the section heading (sanitized and guarded), never in
  metadata, logs or the terminal. **Recommended.** (b) Also in metadata (unguarded).
- **D15 — Markup in attachment text.** (a) `html.escape(quote=False)`, a `\#` escape on leading
  `#`, and control and format characters removed. **Recommended.** (b) Put the text in a fenced
  code block (safe, but less readable, and fences can be closed from inside).
- **D16 — What counts toward the 50.** (a) Every processed attachment, whether fetched or decoded
  inline. **Recommended:** the cap bounds extraction cost as well as calls. (b) Fetches only.
