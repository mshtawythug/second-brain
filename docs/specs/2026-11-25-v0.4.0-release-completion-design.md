## 1. Rules that hold until the tag

- Every change goes through the same path: plan, then TDD (a failing test first), then a PR, green CI,
  code review (`ZERO ISSUES FOUND — APPROVED @ <sha>`) and an audit (`AUDIT PASSED @ <sha>`). The audit is
  a security review for anything handling deletion, untrusted input or restore. A new commit invalidates
  every verdict.
- Merges are done by ops-merge only, with `gh pr merge N --merge --match-head-commit <sha>`, followed by
  the post-merge procedure: fast-forward, ceiling-table check, daemon reinstall plus RECORD diff, watcher
  kickstart, skills sync, and worktree and test-DB cleanup.
- Commits and pushes to fix branches are owner-authorized for the 0.4.0 work (confirmed 2026-11-21).
  Merging to master happens only after review.
- Nothing connects to prod `:55432` except owner-approved operations, and those run only after a fresh
  `brain backup`. `~/brain-vault` and `~/.brain` are never touched by tests.
- **Mutation runs** on guard code need recording fakes for every connect, docker and subprocess path in
  the selected tests, proven before mutating (lesson of the 2026-11-19 incident, §5).
- The release tag is pushed only after the owner says "go tag", because it publishes to PyPI.
